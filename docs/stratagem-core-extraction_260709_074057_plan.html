Problem & Solution

The deployable Stratagem system is entangled with its builder. Deployed skills cite builder-only paths (Steward CLAUDE.md, Meta-Architecture Framework) that dangle on any machine without the builder repos; and the Stratagem-system operating rules are smeared across TWO builder files — C:\code\Stratagem\CLAUDE.md (design surface) and C:\code\CLAUDE.md (workspace config) — neither of which ships cleanly. A fresh consuming project inherits dangling references and cannot reconstruct the rules. Principle: Builder ≠ Artifact. Solution: package the deployable core as a Claude Code plugin (stratagem-core) with one consolidated rules doc, extracting all Stratagem-system logic from both builder files. The plugin references only plugin-relative paths; the builder keeps design-only; the operator keeps personal-only.

✅ RESOLVED — slash-command namespacing (spike 2026-07-09). Plugin commands are always namespaced by the plugin's name (proven live: stratagem-ado → /stratagem-ado:sp; confirmed against Claude Code plugin docs). Decision: name the plugin sg (both plugin.json name AND the marketplace entry — the marketplace name drives the prefix if they differ, so set both) → commands become /sg:cp, /sg:px, /sg:ax, … Cost: a 3-char prefix vs bare /cp — there is no bare-command or aliasing path for plugin skills (mandatory namespace). Non-issue: a plugin /sg:cp and a leftover project-level bare /cp do NOT collide (different namespaces), which also gives a clean migration window. "Stratagem Core" remains the descriptive identity (manifest description); sg is the name/prefix.

Migration & the bootstrapping paradox

The builder uses the product it builds — this very session ran /cp /phx /cf /rs from ISCI-Vision\.claude\skills\. Post-extraction, the single skill source is the plugin. Two sub-questions: (1) Dogfooding — does the builder install stratagem-core to run its own workflows, or keep a working authoring copy? Leaning: builder authors in plugins/stratagem-core/ and dogfoods by installing from the local marketplace (same loop stratagem-ado uses — INSTALL.md §3 local-dir marketplace). (2) Consuming-project migration — ISCI-Vision removes its .claude/skills/ copies and installs the plugin; sequence with a rollback (the preScrub backup is precedent).

stratagem-core ⇄ stratagem-ado relationship

Two sibling plugins: core = the workflow engine (always-on); ado = the optional board bridge (defaultEnabled:false) that consumes core's neutral seams (Sync-Id, the board adapter). Confirm ado's references resolve to core's shipped seams, not builder paths — ado is already scrubbed of identity, but a sweep must confirm it names no builder file either. They compose; neither references the builder.

Configuration-hierarchy impact

The extraction rewrites the layer model in [[configuration-hierarchy]]. Today's 5 layers (global skills → desktop skills → global CLAUDE.md → project CLAUDE.md → Steward CLAUDE.md) collapse: layers 1/3/5's SYSTEM content merges into the plugin. The clean post-state is 3 runtime layers: plugin rules doc (workflow) + project CLAUDE.md (domain) + operator config (personal) — none referencing the builder. The corpus page (itself stale — still documents the retired Wiki Registry) is re-rendered at /rs close-out.

Testing Strategy

  • Grep-clean (self-containment gate): shipped plugin artifacts have 0 hits for Steward / Stratagem\CLAUDE.md / Meta-Architecture Framework / c:\code\Stratagem / c:\code\Steward — enumerated + near-miss sweep.
  • Namespacing spike (pre-commit): a one-skill throwaway plugin proves how the command surfaces (/x vs /plugin:x) — the only gate for the AP-4-analog uncertainty.
  • Fresh-install tracer (the real proof): install stratagem-core into a clean project with NO builder repos on-path; run the full /pf → /cp → /phx → /cf → /rs lifecycle end-to-end. Builder-independence proven only by a live run.
  • Rules-resolution check: a skill that cites the rules doc resolves it via ${CLAUDE_PLUGIN_ROOT} in both CLI and the VSCode extension (AP-2 venue split).
  • Sibling-compose check: stratagem-ado still works alongside stratagem-core, both builder-independent.
  • Residue reads: Stratagem\CLAUDE.md = design-only + ship note; c:\code\CLAUDE.md = operator-only — confirmed by read, not just grep.

Complexity

High. Cross-cutting across ~21 skills + 2 builder CLAUDE.md files + a new plugin + a consolidated rules doc + a live migration of the running system. New abstraction (the plugin as the core's home) and a platform-capability uncertainty (namespacing) that must be spiked. Not single-commit reversible → phase it: (P0) namespacing spike → (P1) scaffold plugin + author rules doc (extract + consolidate) → (P2) move skills + re-point refs → (P3) slim the two builder files → (P4) dogfood-install + fresh-install tracer + migrate ISCI-Vision.

Success Criteria

  • stratagem-core plugin is fully self-contained: 0 builder references in shipped artifacts (grep-clean + near-miss).
  • All SYSTEM rules from BOTH c:\code\CLAUDE.md and Stratagem\CLAUDE.md live in the one package rules doc; the 5 leak refs re-point to it.
  • Stratagem\CLAUDE.md = design-only + one-way ship note; c:\code\CLAUDE.md = operator-only.
  • A fresh consuming project installs the plugin and runs the full lifecycle with zero dependency on the builder repos.
  • stratagem-ado still composes with stratagem-core; both builder-independent.
  • [[configuration-hierarchy]] re-rendered to the post-extraction 3-layer model.
