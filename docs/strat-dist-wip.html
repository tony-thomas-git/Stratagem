Profile — Stencil → Fill → Verify Agreed

Profile turns an inert Core into the fully-functional Stratagem seen on this box. Ships as a blank stencil (format only); filled by a .bat — ask → save → verify, LLM as fallback — the sibling of the Core install script. These are the slots the install must supply (settings · plugin enablement · registry rows · secrets).

🔒 Invariant — Core replaceable, Profile durable
Core install/update writes only Core-owned paths; it never writes a Profile slot, and Core runs without Profile (degrades gracefully — NEW-BOX's "absent registry → no-op, zero regression" proves it for one slot). A working machine's Profile survives every Core update untouched → devs contribute / distribute / install / update Core freely. Mechanism: route each Profile slot to a .local / data file Core never ships (settings.local.json · CLAUDE.local.md · pat.b64), so a Core update can rewrite CLAUDE.md/settings.json without touching Profile.

Profile in Core Assets — externalize + reference Agreed

Principle: parameterize, never personalize. A Core asset holds zero Profile literals. Every Profile value lives in one Profile-owned home; the asset references it via whatever indirection its type allows. Because the value never sits inside the Core file, a Core update overwrites the asset freely and the 🔒 invariant holds. So the answer to "how do we handle Profile in skills / hooks / workflows" is: we don't put it there at all — we externalize it and point at it.

⛔ Anti-pattern — no in-place token-fill
Filling {{PLANS_DIR}} → a real path written into the skill/settings file is wrong: the next Core update overwrites that file and destroys the value. Indirection (reference an external Profile file), never in-place substitution into a Core-owned file.

CLAUDE.md Architecture — parent-level incorporation Objective

How Stratagem manifests across a nested project tree: one parent CLAUDE.md at c:\code carries the system; every project under it inherits automatically because CLAUDE.md crosses git-repo boundaries. This is the mechanism behind today's MVP — Core running in ISCI-Vision.

The 5 cascade rules that make this work (confirmed via docs.claude.com):

#RuleConsequence for us
1Merge, not replace — every CLAUDE.md from filesystem-root → cwd is concatenatedparent + project rules add, never clobber
2Deeper wins — on conflict the closer-to-cwd file overridesa project can override a Stratagem default; Profile .local wins over all
3Crosses git repos — walks to the filesystem root, does NOT stop at a project's .git (unlike skills)✅ proven live — c:\code\CLAUDE.md loads inside every project repo
4Load order — managed → ~/.claude → root-down-to-cwd; within a dir, CLAUDE.md then CLAUDE.local.md.local gets the last word → Profile overrides cleanly
5Nested on-demand — a subdir's CLAUDE.md loads when Claude touches files theremonorepo packages self-describe; unused at top level

◎ Objective — Stratagem lives at the parent
Core ships its cross-cutting rules as one CLAUDE.md at the workspace parent (c:\code here; wherever a dev keeps projects otherwise — the path is a Profile/install choice, the content is Core). One file → Stratagem in every project. Why the parent, not ~/.claude: it scopes Stratagem to coding work, leaving ~/.claude for truly-universal personal prefs. Today's gap: the deep Meta-Architecture prose still sits in c:\code\Stratagem\CLAUDE.md (project-level) → it does NOT load during ISCI-Vision sessions. Incorporation = hoisting the cross-cutting rules up to c:\code\CLAUDE.md.
