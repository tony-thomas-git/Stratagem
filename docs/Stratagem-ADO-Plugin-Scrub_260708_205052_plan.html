Problem & Solution

The Core scrub made the 23 Stratagem skills portable. But stratagem-ado — also a distributable — still bakes in your identity: org intelliscience, owner tony.thomas@intelliscience.com, default project ISCI - Consolidated - Kanban. A second dev can't install it as-is. Solution: give the plugin one self-contained identity home in its own data dir (alongside pat.b64), read by both the MCP launcher and the skills — so the plugin carries zero identity literals and needs no session env vars.

Surface = 3 values: org (×3: .mcp.json + 2 board URLs), owner (×1: sp), project default (×2: sp, pr). ss already externalized them — but to session env, the wrong home. The launcher is already parameterized (reads --org from args).

Key Insight — the shim already solves this

The launcher's own comment (D15): "a plugin's .mcp.json does string substitution only — it CANNOT read a file's contents into an env value." That's exactly why the pat.b64 shim exists — it reads the secret file and exports it. The same shim can read the org (and project) from a config file in ${CLAUDE_PLUGIN_DATA}. So the plugin's identity gets the same treatment as its secret: a file in the data dir, read by the launcher — and by the skills (they already glob that dir for pat.b64).

Corpus grounding (Stratagem-Vault)

This plan reuses a documented pattern, not a new invention. [[bundled-mcp-launcher-shim]] is exactly this shape (shim reads ${CLAUDE_PLUGIN_DATA}/<file> → env → execs the pinned server) — from the original stratagem-ado-plugin build. One revision: that pattern kept the org declarative in .mcp.json (readability + grep-verify) because it treated org as fixed config. The scrub reclassifies org as per-install Profile (like the secret) → it moves into the launcher-read config, and .mcp.json stops naming it. Deliberate pattern evolution — worth an /rs note after.

[[claude-code-plugin-bundled-mcp-gotchas]] — the launcher edit MUST preserve AP-1 shell:true (else spawn EINVAL on Node ≥20) and AP-2 the node-dir PATH prepend (else the VSCode extension can't find npx). AP-3 (.mcp.json can't read files) is the very reason the shim reads the config. All are env-coupled — invisible to grep/node --check; only a live launch catches them.

Architecture — one identity home

${CLAUDE_PLUGIN_DATA}/ado.config.json
{ org, project } — non-secret Profile → read by → launcher ado-mcp-launch.js
passes --org from config  &  skills sp · pr · ss
org/project defaults + board URLs
  • New file: ${CLAUDE_PLUGIN_DATA}/ado.config.json = { "org": "...", "project": "..." } — the plugin's non-secret identity, sitting beside pat.b64 (the secret). Both gitignored (data dir, per-install).
  • Owner is derived from pat.b64 — it's base64("email:PAT"), so decode → email. One source; no duplication.
  • Launcher reads ado.config.json (like it reads pat.b64) and supplies --org itself → .mcp.json drops the hardcoded --org intelliscience.
  • Skills resolve org/project from the same config (newest-wins glob, same as the PAT), owner from the decoded PAT; build board URLs as https://dev.azure.com/<org>/… from the resolved org.
  • ss re-target: replace $env:STRATAGEM_ADO_* with the config reads → and delete the STRATAGEM_ADO_* env from ISCI-Vision\.claude\settings.local.json (subsumed — confirms env-promote would've been throwaway).

Testing Strategy

  • MCP still connects (live tracer — the only gate for env-coupled defects): restart → core_list_projects returns the Kanban project, run in BOTH the CLI and the VSCode extension (AP-2: they spawn MCP with different PATHs). Proves the launcher resolves org from config + PAT.
  • Skills resolve from config: a dry /stratagem-ado:sp (or ss) banner shows org/project/owner sourced from config/PAT, not hardcodes.
  • Grep-clean: plugin source (skills + .mcp.json + launcher) has 0 hits for intelliscience / the email / Kanban (the values now live only in the gitignored data-dir config).
  • Portability proof: a hypothetical second identity (different ado.config.json + pat.b64) would drive a different org/project with no source change.

Success Criteria

  • Plugin source carries zero identity literals; identity lives once in ado.config.json + pat.b64 (both per-install data).
  • MCP connects; sp/pr/ss resolve org/project/owner from that one home.
  • ss no longer uses $env:STRATAGEM_ADO_*; the env block is gone from settings.local.json.
  • Plugin is now as portable as Core — installable by any dev with their own PAT + config.

Complexity

Medium. ~6 touch points (1 new config, 1 Node launcher edit, .mcp.json, 3 skills) + 1 env deletion. Change-coupled (launcher ↔ .mcp.json ↔ config). Requires an MCP restart to verify. No new abstractions — reuses the existing pat.b64-shim pattern for the org.
