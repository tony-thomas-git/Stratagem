1 · What we're building

A new general (core-bodied) skill, /map, that prints the canonical lifecycle as ASCII to the terminal by default, and — via a --html flag — writes a .html context-swimlane in the framework's existing visual language (the 5-category color legend + emoji vocabulary from stratagem-testing-workflow.svg). It is static: no plan discovery, no git reads on the default path — the um ethos ("emit and stop, never explain the output"). Because it lives in core/skills/, the directory-driven compiler ships it into all five flavors (coder / author / business / sales / tester) with zero registration.

2 · Architecture approach

  • Directory-driven, no manifest. compile.mjs:625 compiles every core/skills/*.md. Dropping map.md in is the entire registration — the profile (T15) precedent exactly.
  • Vars-only seam, no overlay. Like profile/um, the only per-flavor divergence is frontmatter + branding, which overlays can't reach — so no templates/*/overlays/map.overlay.md. Composes through the standard pipeline ① overlay → ② include → ③ substitute → ④ header.
  • Branding via {{MAP_TITLE}} (resolves the "STRATAGEM is ok" note). The purity lint (lint-core-purity.mjs:52) hard-fails on the literal token Stratagem anywhere in core/. So the ASCII/HTML title is a {{MAP_TITLE}} var: a neutral, lint-clean default in core/vars.yaml, and a STRATAGEM · lifecycle map override in each flavor's templates/<flavor>/vars.yaml (the lint scans core/ only, never templates/). Every shipped flavor renders STRATAGEM; the neutral default only ever exists in the unshipped core build. This is the same brand-restore pattern WIKI_INGEST_DESC already uses.
  • The map is its own source of truth. The literal ASCII lives in map.md; the --html render is generated from the same fixed node/edge model on each run. Static art embedded in a skill body is idiomatic here (um's status block, the banner fragment).

4 · The drift guard — the one decision to sign off

Finding that reshapes the seed's H-question: the existing diff-harness/golden gate does not catch map drift. Golden proves the compiled bytes match a frozen snapshot — but if a skill is renamed and map.md isn't updated, map.md is unchanged, so it compiles identically and golden stays green. The map silently lies. A dedicated content test is required.

Recommendation (a + focused test): hardcode the map in map.md for legibility, and add map-drift.test.mjs that:

  • No dangling refs: every /token the map names resolves to an existing core/skills/<token>.md — catches a skill renamed out from under the map.
  • Spine present: the canonical lifecycle set {ps,pf,cp,px,ax,ex,fx,cf,rs} all appear — catches a lifecycle skill dropped from the map.

This is cheap, deterministic, and catches both drift directions golden can't. It de-risks the seed's H decision down to M. Rejected alternatives: (b-only) golden — proven blind above; (c) generate the map from a manifest at compile time — most robust but the most machinery, deferred as a possible v2.

Sign-off needed: approve the drift-test approach (vs. accept silent drift, or go straight to generation). Everything else in this plan is L/M and auto-proceeds under Trust-But-Verify.

5 · Integration points

  • Compiler op ③ resolves {{MAP_DESC}} + {{MAP_TITLE}} from merged vars (template-wins). Reserved-name guard is irrelevant (neither is a built-in).
  • lint-core-purity must stay green — the whole reason branding is a var. Verify map.md + the core vars.yaml additions carry no Stratagem/stack/language/absolute-path tokens.
  • diff-harness / golden — re-baseline all five flavors so the new map dir is PASS, not MISSING.
  • Flavor fan-out is the only "horizontal" surface: one source, five outputs. Handled entirely by the compiler + the per-flavor MAP_TITLE override + the golden re-baseline. No per-flavor logic.
