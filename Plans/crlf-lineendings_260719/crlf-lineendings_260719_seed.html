CRLF line endings break /if at the Workflow approval gate

2026-07-19 · scope/workflow · repo: Stratagem & Stratagem-Core · status: uncommitted, awaiting review

The unattended /if loop cannot launch because its Workflow script autonomy-loop.js reaches the harness with CRLF line endings, which the approval dialog will not render. This is not a code defect and not a plan defect — it is a line-ending policy gap at git checkout that a one-word change to a single .gitattributes line closes at the source.

1 · Problem / why this exists

The need. /if is the only unattended, budget-guarded execution path (the P2 autonomy loop). It is blocked today: the Workflow permission dialog refuses to display a script that contains carriage returns, so the operator can neither review nor approve the launch. The interactive /phx fallback exists, but the /if path itself must not ship broken — it is a distributed capability.

Why it exists as a problem. The corruption is latent and recurring, not a one-time accident. A manual CRLF→LF fix was already applied once (evidence: a autonomy-loop.js.crlf.bak dated Jul 17 sits beside a now-LF copy), but nothing at the source prevents the next checkout or the next hook copy from re-introducing CRLF. The intended outcome is a durable fix: the shipped scripts are LF everywhere, on every platform, by policy — so /if renders and the fix cannot silently regress.

2.2  The root-cause line — git's own verdict

The distributed .gitattributes (in Stratagem-Core) reads:

# Normalize line endings in the repo (LF), let git present native in each working copy. * text=auto *.js text ← the gap: "text" WITHOUT "eol=lf" *.md text *.json text

git check-attr -a on the workflow file returns text: set — not eol=lf. text alone means "normalize to LF in the object store, but check out platform-native." On Windows with core.autocrlf=true (confirmed in both repos), native = CRLF. That is the entire mechanism.

2.3  The causal chain

Blob is clean; CRLF is injected at checkout and byte-copied downstream. Force eol=lf at step 1 and every downstream copy inherits LF — no hook change needed.

2.4  Same gap, second victim — the sync hook

The SessionStart sync hook sync-autonomy-workflow.sh is itself governed by * text=auto and ships CRLF (39/39 CR/LF) — a \r-terminated shebang (#!/usr/bin/env bash\r). On strict shells this fails with bash\r: No such file or directory. And because the hook's contract is best-effort / always exit 0, such a failure is invisible — it degrades silently. The narrow "workflows only" scope would leave this second failure in place.

3 · Shape of the idea

One layer, at the source (architect's choice — no hook-code change):

  1. Amend .gitattributes in Stratagem-Core (the ADO distribution repo the marketplace clones — not the CWD GitHub Stratagem repo). Add a later, more-specific line so last-match-wins forces LF:
    **/workflows/*.js  text eol=lf   # recommend also: *.sh text eol=lf
  2. Renormalize + republish. git add --renormalize ., commit, publish; the marketplace re-checks-out LF, the hook cp carries LF through to the consumed path. No hook change required — .gitattributes-only holds because the marketplace is a verified git checkout (autocrlf=true, blob LF) that attributes reach.
  3. Remediate existing artifacts (now). Renormalize the working tree, flip the CRLF bundle/marketplace copies, and delete the stale autonomy-loop.js.crlf.bak.

Why source-only works here: the corruption is a smudge, not a stored byte. Fix the smudge rule and the LF-clean blob presents as LF everywhere it is checked out or copied.

4 · Open questions for /pf

Q1 — Two-repo split. The shipped .gitattributes lives in Stratagem-Core (ADO); the CWD Stratagem (GitHub) repo has none at all. The fix must land in Stratagem-Core to reach the distribution. Does CWD Stratagem also get its own .gitattributes for working-tree hygiene (its bundle is CRLF at 288), or is it out of scope? Which repo is the canonical source of the distributed policy needs an explicit ruling.
Q2 — "Workflows only" vs the .sh hook. The architect chose the narrowest scope (workflows/*.js). But the sync hook *.sh is measurably CRLF and can fail silently. Recommend extending to *.sh text eol=lf — one extra line, closes the second failure. Accept the wider line, or hold the narrow scope on purpose?
Q3 — Marketplace re-checkout timing. .gitattributes governs future checkouts. Already-checked-out CRLF files in the marketplace clone flip only on re-clone or an in-clone renormalize — which the plugin system controls, not us. What is the actual publish→re-sync path, and does "remediate now" (§3.3) reach the consumer, or only the repos we control?
Q4 — Verify the symptom→cause link. The census shows the consumed copies are LF right now, so /if should already render post-manual-fix. Before closing, confirm the durable fix produces a clean /if launch (the testable prediction), rather than assuming CRLF was the sole blocker.
Q5 — Sync-hook reliability aside. The consumed copy is a newer 388-line LF file while the bundle is a stale 267-line CRLF file — if the hook had run, it would have downgraded the consumed copy. It has not. Worth a follow-up: is the hook actually running/succeeding? Out of scope for the CRLF fix, but flagged. (inferred from mtimes + size delta)

5 · Non-negotiables (carried from the architect)

N1. The sync hook stays best-effort / skip-loud / always exit 0. Any remediation must not add a failure path to session start.
N2. Never-commit rule. This seed and its plan do not commit or push; changes are left uncommitted for manual review.
N3. Simple, surgical, good code (codevelopment axiom). Prefer the one-line .gitattributes change over any clever normalization script. The chosen path is .gitattributes-only precisely because it is the smallest change that fixes the source.
N4. The consumed .claude/ path is gitignored — never under git control. The fix must therefore hold via the checkout→copy chain, not via tracking that file.
